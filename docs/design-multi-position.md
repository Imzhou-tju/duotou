# 同一单位投递多个岗位 · 前端方案设计

> 状态：**已实现并上线**（`draftUnits` 单位-岗位三层结构、单位卡 + 岗位内联行、扁平展开提交、上限/重名/空卡校验）。
> 第 7 节的落地步骤仅作实现记录保留；实现细节以代码为准（`app.js` 的 `renderUnits / renderPositions / saveGroupRecord / saveRecord`）。

> 目标：把「岗位」从「一行一个岗位」的标量，提升为「单位下的岗位数组」，
> 让集团 → 单位 → 岗位 三层在表单里一一对应，后台按岗位生成多条投递记录。

## 0. 现状（方案要接住的既有实现）

| 项 | 现状 |
| --- | --- |
| 数据模型 | 单表 `applications`，**一条 = 一个单位 + 一个岗位**；没有单位表、没有岗位字典表 |
| 集团模式 | `draftGroupRows` 每行 = `{sub, pos, base, date, remark}`，即「一行 = 一个单位 + 一个岗位」 |
| 单单位模式 | 单个岗位输入框 + 「批量」textarea（每行一个岗位，其余字段共用，一次 insert 多条） |
| 保存 | 新增 `insert([...rows])`；编辑只 `update` 当前这一条 |
| 样式基线 | 单位行 = `.g-row` 卡片（1px 边框 / 12px 圆角 / focus-within 高亮 brand 色） |

**痛点**：同一单位投 2 个岗位，现在要填两行、把单位名 / Base / 日期 / 备注重复填两遍。

## 1. 交互设计

### 候选方案对比

| 方案 | 说明 | 评价 |
| --- | --- | --- |
| A. 下拉多选岗位 | 从岗位字典里勾选 | ✗ 本项目没有岗位字典，校招岗位名是自由文本 |
| B. 每个岗位一张完整卡片 | 岗位各自带 Base / 日期 / 备注 | ✗ 同单位共用信息被复制 N 份，视觉膨胀，且现有设计已明确「Base / 日期按单位走」 |
| C. 岗位卡片列表（chip 标签流） | 已选岗位以 chip 展示，点 + 弹层输入 | 中：已选状态直观，但编辑已有岗位名要二次进入弹层，改字麻烦 |
| **D. 单位卡 + 岗位内联行（推荐）** | 单位卡内竖向列出岗位输入框，底部「＋ 添加岗位」 | ✓ 岗位名短文本，一行输入即可编辑；共用字段留在单位层；增删成本最低；与现有 `.g-row` 风格同构 |

### 推荐：D — 单位卡 + 岗位内联行

**集团投递模式**

```
┌ 集团名称*：[中粮集团            ]（自动归并提示）
│
├ 单位卡 1 ────────────────────────────────  [× 删除该单位]
│   具体单位/分行*：[中粮粮谷            ]
│   Base 地：[成都   ]   投递日：[2026-10-01]
│   备注：[内推码 A1                        ]
│   该单位下的岗位
│     [AI 应用开发岗                ] [×]
│     [软件开发岗                  ] [×]
│     ＋ 添加岗位
│
├ 单位卡 2 ────────────────────────────────  [×]
│   ……
│
└ ＋ 再加一个单位
   投递链接（本集团共用）：[https://…]
   共将创建 N 条投递记录
```

**单个单位模式**（复用同一套岗位列表组件）

```
单位名称*：[字节跳动        ]
二级单位 ：[抖音            ]
集团名称 ：[               ]（选填，已归入集团时提示）
岗位名称
   [后端开发                    ] [×]
   [算法工程师                  ] [×]
   ＋ 添加岗位          [批量粘贴]
Base 地 / 投递链接 / 备注 / 各阶段日期（整单共用）
```

- 「批量粘贴」保留现有 textarea 能力：粘贴多行 → 解析成岗位行（与列表同一数据结构，不再两套逻辑）。
- 单个单位模式本质是「只有一张单位卡」的集团模式，两种模式共用 `draftUnits`，渲染差异只在是否显示「单位名」字段。

## 2. 布局与视觉

| 层级 | 视觉处理 | 说明 |
| --- | --- | --- |
| 单位卡 | 沿用 `.g-row`：1px `--border`、12px 圆角、`--bg` 底，聚焦时边框转 `--brand` | 与现有卡片完全一致，不引入新语言 |
| 岗位行 | 新 `.p-row`：**无外框**、高 44px、行间 1px `--border` 细分隔线、右侧 32×32 删除按钮 | 比单位卡「轻一级」，层级靠留白与分隔线区分，避免卡片套卡片 |
| 添加按钮 | `.g-add` 同款虚线/浅底小按钮，文字左对齐，位于岗位区底部 | 与现有「＋ 再加一个投递」视觉一致 |
| 高度变化 | 页面整体由 `.edit-scroll` 滚动承载，新增/删除岗位时**不做内嵌滚动**，避免嵌套滚动条 | 增删一行 ±48px，动效可选 120ms height/opacity 过渡，不做位移抖动 |
| 空态 | 至少保留 1 个岗位行，placeholder「岗位名称，选填」；行下方小字「不填岗位也会生成 1 条记录」 | 兼容现有「只投单位不明岗位」的数据 |
| 达上限 | 「＋ 添加岗位」置灰不可点，文案变「最多 10 个岗位」 | 不用弹 toast 打断输入 |
| 计数反馈 | 集团模式底部动态显示「共将创建 N 条投递记录」 | N = Σ 各单位岗位数（岗位全空的单位计 1 条） |

## 3. 约束与校验

| 规则 | 取值 | 前端处理 | 提示文案 |
| --- | --- | --- | --- |
| 每单位岗位上限 | **10** | 达上限后按钮置灰 | 「最多 10 个岗位」 |
| 单位数上限（集团） | **20** | 达上限后「＋ 再加一个单位」置灰 | 「单次最多添加 20 个单位」 |
| 单次提交记录上限 | **60** | 超限阻止保存并 toast | 「一次最多提交 60 条投递，请分批添加」 |
| 同单位岗位去重 | trim + 去空格 + 全角转半角 + 忽略大小写后比较 | 添加/失焦时校验，重复则不新增并把焦点移到已存在的那行 | 「「AI 应用开发岗」已经添加过了」 |
| 岗位名长度 | ≤ 40 字 | `maxlength=40`，超限截断 | 无（输入即限制） |
| 必填 | 集团模式：集团名、单位名必填；单单位模式：单位名必填；**岗位可全空** | 保存时校验并聚焦第一个空项 | 「集团名称必填」/「请填写单位名称」 |
| 删除后保留 | 至少 1 个岗位行；只剩 1 行时隐藏删除按钮 | 删除按钮 `hidden` | — |
| 删除单位 | 至少 1 张单位卡；只剩 1 张时隐藏单位删除按钮 | 同上 | — |
| 编辑态删除 | 岗位行若带 `id`（库中已有记录），删除时二次确认 | `confirm()` | 「删除后该投递记录也会从列表移除，确定？」（仅对已存在记录提示） |

## 4. 数据结构

### 4.1 表单状态

```js
// 集团 / 单单位两种模式共用；单单位模式就是「只有一张单位卡」
let draftUnits = [
  {
    key: 'u1',                 // 前端临时 key，用于渲染与事件定位
    recId: null,               // 编辑时：该单位对应记录 id（新增为 null）
    sub: '中粮粮谷',           // 具体单位 / 二级单位
    base: '成都',
    date: '2026-10-01',
    remark: '内推码 A1',
    positions: [
      { key: 'p1', recId: null, name: 'AI 应用开发岗' },
      { key: 'p2', recId: null, name: '软件开发岗' },
    ],
  },
];
```

- 每个岗位是对象（带 `recId`），因为**编辑已有岗位必须 update 原记录，新增岗位必须 insert**，扁平字符串数组做不到这一点。

### 4.2 提交给后台的格式（推荐：扁平展开，不是 unitId + positionIds）

```js
// 展开：每个岗位一条记录
const payload = [];
for (const u of draftUnits) {
  const list = u.positions.length ? u.positions : [{ recId: u.recId, name: '' }];  // 岗位全空 → 该单位仍出 1 条
  for (const p of list) {
    payload.push({
      id: p.recId,                       // 有 → update，无 → insert
      company: group || company,
      group_name: isGroup ? group : null,
      sub_unit: u.sub || null,
      position: p.name.trim() || null,
      base: normalizeLocation(u.base) || null,
      link,                              // 本单共用
      remark: u.remark || null,
      stage: stageFromDates(stageDates) || '投递',
      stage_dates: stageDates,
      apply_date: stageDates['投递'] || null,
      update_time: new Date().toISOString(),
    });
  }
}
// 分流执行：withId → sb.update(...).eq('id', id)；无 id → sb.insert([...]).select()
```

**为什么不采用 `{unitId, positionIds: [...]}`**：
1. 后端是单表，没有 `units` / `positions` 实体表，也不存在稳定的 `positionId`（岗位名是自由文本，用户每次手打）；
2. 新建场景下 `unitId` 尚未生成，前端拿不到；
3. 现有 `saveGroupRecord()` 已经是「展开成多条 insert」的路子，继续沿用改动最小、风险最低。

**演进**：若将来引入岗位字典表（岗位有 id、有 JD），再改为
`{ unitId, positionIds: [12, 87] }` + 后台展开，前端只传 id，文案由字典维护。

### 4.3 保存后的回填

- 新增：`insert(...).select()` 拿回新 id → `loadRecords()` 全量刷新（与现状一致）。
- 编辑：只 update 本次表单里的记录；**同单位下未进入表单的其他岗位不受影响**（它们本来就是独立记录）。
- 若用户在编辑态新增了岗位行 → 该行走 insert，其余走 update，两条路径都要 `await`。

## 5. 响应式与边界

| 场景 | 处理 |
| --- | --- |
| 移动端（<720px） | 单位卡内全部竖向堆叠：单位名 → Base / 投递日（一行两个）→ 备注 → 岗位行列表 → ＋添加岗位；删除按钮 32×32 触控区 |
| 桌面端（≥720px） | `.form-card` 已是两列网格；单位卡设 `grid-column: 1 / -1` 跨整行，卡内再分两列：左列「单位 / Base / 日期 / 备注」，右列「岗位列表」；岗位行在卡内单列纵向 |
| 小屏（<360px） | 岗位输入框与删除按钮同一行，输入 `min-width: 0` + `flex:1`，按钮固定 32px，避免挤压 |
| 岗位很多时 | 不做内嵌滚动，交给 `.edit-scroll` 整页滚动；岗位 ≥6 个时单位卡头部显示「已选 N 个岗位」便于回看（P1） |
| 单位很多时 | 集团模式单位卡 ≥8 张时，除当前聚焦卡外自动收起为一行摘要（P1，本期不做） |
| 键盘/无障碍 | 「＋ 添加岗位」点击后自动聚焦新行；删除后焦点移到上一行；岗位 `aria-label="岗位名称 N"` |

## 6. 关键交互状态

| 状态 | 表现 |
| --- | --- |
| 默认 | 1 张单位卡 + 1 个空岗位行，占位文案「岗位名称，选填」 |
| 新增岗位 | 点「＋ 添加岗位」→ 列表尾部追加空行并聚焦；按钮未达上限时常亮 |
| 删除岗位 | 行右侧 × ；只剩 1 行时 × 隐藏；删除后焦点上移 |
| 重名 | toast 提示 + 焦点跳到已存在的那行并选中文本，新行不留空 |
| 达上限 | 按钮置灰、文案改为「最多 10 个岗位」 |
| 岗位空 | 保存时该单位仍生成 1 条 `position = null` 的记录（兼容旧数据） |
| 保存中 | 保存按钮禁用，文案「保存中…」，防重复点击 |
| 保存成功 | toast「已添加 N 条投递」（N = 实际写入条数），返回首页并刷新 |
